## Notes on the runs

- **Final submission:** Salesforce/SFR-Embedding-Code-400M_R with `no_examples_compact` query cleanup and raw code, max 1024 tokens: **NDCG@10 0.51391, MRR@10 0.46956** (baseline 0.05638 / 0.04820). It is copied to `appsretrieval_results.json` in the repo root and attached to the GitHub release.
- **Baseline:** the provided baseline (bge-small-en-v1.5, NDCG@10 0.05638, MRR@10 0.048195) is reproduced exactly by `--model bge-small-inst`, which uses bge's standard query instruction "Represent this sentence for searching relevant passages: ". Without the instruction bge-small gives 0.05142. `baseline_bge_small.json` is the reproduced run.
- **Query cleanup modes** (`--query-mode`): `full` = problem statement as given; `no_examples` = cut from the "-----Examples-----" / "-----Note-----" header to the end; `compact` = turn "-----Input-----" rules into "Input:" and squash whitespace; `no_examples_compact` = both.
- **Wall time** is the whole MTEB evaluate call. Runs that only changed the query cleanup reused the cached corpus embeddings (the encoder caches embeddings by exact input text in `~/.cache/prism_eval`), so their wall time is mostly query encoding. Several runs also shared the CPU with other jobs (the "Threads" column is torch threads for that run), so wall times are rough.
- **codesage/codesage-small-v2** was not measured: its remote code does not import with transformers 4.56.
- **Code cleanup** (`--doc-mode strip|nocomment`) is implemented but was not measured; we stopped that run to save time.

## BM25 and hybrid fusion (offline check, not an MTEB run)

`prism/eval/hybrid_check.py` loads the cached CodeRankEmbed embeddings (full queries, raw code) and computes NDCG@10 / MRR@10 with its own implementation. That implementation reproduces the dense MTEB number (0.2355 vs 0.23539), so the comparison is fair.

| Ranking | NDCG@10 | MRR@10 |
|---|---|---|
| CodeRankEmbed dense only | 0.2355 | 0.2060 |
| BM25 only (identifier tokens, rank_bm25) | 0.0154 | 0.0131 |
| RRF dense + 0.2 x BM25 | 0.2280 | 0.1955 |
| RRF dense + 0.5 x BM25 | 0.2131 | 0.1773 |
| RRF dense + 1.0 x BM25 | 0.1731 | 0.1420 |

BM25 is weak here because a problem statement and its Python solution share very few words, and fusing it in only adds noise. So the benchmark submission is dense only. The CLI still uses hybrid search, because real code search queries often contain identifiers (see the README).
